# Closing an 8.7 km LiDAR SLAM loop

During my NavINST internship I wanted to go past LiDAR odometry and actually close a full urban loop. The vehicle drove an 8.7 km route and came back to where it started. On paper that is a loop-closure problem. In practice the stock pipeline still ended ~93 m away.

This post is about how I got that gap down to 3.15 m — not by tuning one threshold, but by finding two separate bugs and fixing the pipeline end to end.

## The setup

I ran a LiDAR-only SLAM pipeline on the [NavINST](https://arxiv.org/abs/2502.13863) Urban01 daytime route using [KISS-SLAM](https://arxiv.org/abs/2503.12660) on top of [KISS-ICP](https://arxiv.org/abs/2209.15397). The estimator only saw Velodyne VLP-16 scans. GNSS/INS stayed out of the run and was used afterward for evaluation.

The high-level flow: deskew each scan, estimate motion with ICP, build ~100 m local submaps, search for revisits, verify matches geometrically, then optimize a pose graph.

Stock KISS-SLAM already helped. With loops enabled it beat a no-loops baseline on several metrics. But it still missed the obvious one: the car clearly returned to the start, and the trajectory did not.

That was the clue. Loop closure was doing something — just not enough.

## Bug 1: timestamps were paired with the wrong points

A spinning LiDAR captures points at different times. To deskew a scan you need each point's XYZ **and** its timestamp to stay matched.

The reader filtered out invalid XYZ rows but kept the original timestamp array. So point `i` could get timestamp `j`. On the first scan alone, ~99.95% of retained points had the wrong time.

The fix was small but strict: apply one mask to both arrays.

```python
valid = ~np.any(np.isnan(points), axis=1)
valid_points = points[valid]
valid_times = timestamps[valid]
```

That cleaned up local motion error a bit. It did **not** fix the missed final loop — which told me there was a second problem downstream.

## Bug 2: the right loop never got a fair ICP shot

When I looked at the start and end scans side by side, the geometry was clearly similar. So why no closure?

Because **finding** a candidate and **proving** it are different steps.

Place retrieval proposes old submaps that might match. ICP then checks whether the 3D clouds actually align. Stock KISS-SLAM mostly took its top descriptor guess and ran fine ICP immediately. Fine ICP only works if the initial guess is already close.

Maps 0 and 81 did overlap. With a good initialization, the overlap test passed. The system just was not giving that pair a wide enough chance during the online run.

## What I changed

I added a conservative top-k verifier:

- keep the top 5 descriptor candidates, not just 1
- reject obvious bad matches early (too close in time, too far apart in space)
- run coarse-to-fine ICP on weaker candidates before the strict overlap test
- accept at most one loop edge per event

<Callout variant="note" title="The design goal">
  Improve recall on hard revisits without filling the graph with false loops. Every accepted edge still had to pass the same geometric overlap bar.
</Callout>

That recovered eight loops online, including the final `0 → 81` link near the route start. I also validated each edge against saved submap geometry and held-out INS motion so I was not just trusting a prettier plot.

## Results

Compared against time-corrected stock KISS-SLAM on the same repaired LiDAR front end:

| Metric | Stock | Improved | Change |
| --- | ---: | ---: | ---: |
| End-to-start gap | 93.1 m | **3.15 m** | **96.6% lower** |
| Horizontal APE RMSE | 22.5 m | **10.4 m** | **53.9% lower** |
| Heading RMSE | 2.25° | **1.69°** | **24.9% lower** |
| 100 m translation RPE | 2.83 m | 2.81 m | ~flat |

The big wins are global: the route closes and horizontal error drops a lot. Local motion barely moves, which makes sense — both runs share the same odometry front end. Vertical error is still high (~37 m), so this is a strong horizontal loop-closure result, not a finished 3D navigation stack.

Evaluation had its own lesson. My first metrics pass reported nonsense like 134 m of drift per 100 m driven for every run. That turned out to be a body-frame conversion mistake, not bad LiDAR. Fixing the axis convention before trusting the numbers mattered as much as fixing the SLAM logic.

## What I took away

- Small data-loading bugs can look like algorithm failures. Timestamp parity is part of the sensor model.
- Retrieval and verification are a team. A stricter ICP step cannot save a candidate that retrieval never surfaces.
- One good headline metric is not the whole story. Closing the loop and fixing horizontal drift still left elevation basically unchanged.
- For a project like this, evaluation is half the work. Frame conventions, alignment, and what you choose to measure need the same care as the estimator.
